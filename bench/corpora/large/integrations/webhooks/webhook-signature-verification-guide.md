# Verifying webhook signatures

This is the internal version of the integrator guide page, with the failure modes support sees. The mechanism: every delivery carries `X-Halden-Timestamp` (unix seconds) and `X-Halden-Signature` (`sha256=<hex>`), where the hex is HMAC-SHA256 of the string `<timestamp>.<raw body>` with the subscription secret as key.

## The rules

1. Read the **raw** request body bytes. Not the parsed JSON re-serialised. Any framework that gives you an object first has already lost the byte sequence (key order, spacing, unicode escapes). Every language has a way to get the raw body; the guide names it for the common frameworks.

2. Build `timestamp + "." + rawBody`, compute HMAC-SHA256 with the secret, hex-encode lowercase.

3. Compare with constant-time comparison against each value in `X-Halden-Signature` (comma-separated during a rotation window, see [[webhook-subscription-management-api]]). One match is enough.

4. Reject if `|now - timestamp| > 300` seconds. This is the replay protection. Our replays ([[webhook-replay-tool]]) re-sign with the current time, so a legitimate replay always passes; an attacker holding an old request does not.

5. Only then parse the JSON.

## Mistakes we see, by frequency

From support tickets tagged `integration:webhook` with sub-tag `signature`, 2026 H1, 47 tickets:

- **Parsed then re-serialised body** (21). PHP `json_encode(json_decode($body))` changes `1.0` to `1` and escapes slashes. Python `json.dumps(request.json)` reorders nothing but changes spacing. Node body-parser without the `verify` hook. The symptom is "signature valid for some events, not others", because some payloads survive a round trip and some do not.

- **Wrong secret** (11). Copied from another subscription, or from staging. The web screen shows the first 4 characters of the secret's hash next to each subscription since HF-3104 so people can tell which is which without seeing the secret.

- **Clock skew** (7). A server without NTP, 8 minutes off, rejects everything. The symptom is "all signatures invalid since Tuesday". The error message in their logs says signature, not time, because their code checks the time after the HMAC and reports the wrong one. Our guide says check time first.

- **Signing the timestamp with a colon or without the dot** (4). Reading the guide too fast.

- **Header case** (3). Some frameworks lowercase header names; `X-Halden-Signature` becomes `x-halden-signature`. Fine, HTTP headers are case-insensitive; their code compared case-sensitively.

- **Uppercase hex** (1). We send lowercase. Compare lowercase.

## Reference snippets

The guide has these; the internal test suite runs them against the vectors below.

PHP:

```php
$expected = hash_hmac('sha256', $ts . '.' . $raw, $secret);
$ok = false;
foreach (explode(',', $header) as $sig) {
    $ok = $ok || hash_equals('sha256=' . $expected, trim($sig));
}
```

Python:

```python
mac = hmac.new(secret.encode(), f"{ts}.".encode() + raw, hashlib.sha256).hexdigest()
ok = any(hmac.compare_digest(f"sha256={mac}", s.strip()) for s in header.split(","))
```

Node:

```js
const mac = crypto.createHmac('sha256', secret).update(`${ts}.`).update(raw).digest('hex');
const ok = header.split(',').some(s => crypto.timingSafeEqual(Buffer.from(`sha256=${mac}`), Buffer.from(s.trim())));
```

(The Node one must guard the length before `timingSafeEqual`, the guide's full version does.)

## Test vectors

Published on the docs site so integrators can unit test without a subscription. Secret is the literal string `test-secret-do-not-use`, timestamp `1700000000`, body `{"event":"ping","id":"00000000-0000-7000-8000-000000000001"}`. The expected signature is on the docs page and in `tests/Webhook/SignatureVectorsTest.php`; it is regenerated by the test, not hand-copied, so the two cannot drift.

## What we do not do

We do not sign headers, only timestamp and body. We do not offer a "disable signature check" mode, even for staging; staging has its own secrets. We do not include the secret in any log, and the relay redacts the `Authorization`-like headers a customer's endpoint might echo back in an error body.

## When support cannot help

If the integrator insists the signature is wrong and their raw body is right, L2 can fetch the exact bytes we sent for a given `delivery_id` (`hfctl webhooks delivery-body <id>`, stored 30 days) and the integrator compares byte for byte. In 47 tickets, this step has never found a fault on our side. It has found a proxy that re-encoded the body twice.

## Rotation walkthrough for integrators

The guide's rotation section, kept here because support paraphrases it often:

1. Call rotate (or click "Rotate secret"). Copy the new secret; it is shown once.

2. Deploy your verifier with **both** secrets accepted. Any delivery during the next 24 hours carries two signatures; your code needs one match with either secret.

3. After 24 hours, remove the old secret from your configuration. Deliveries carry one signature again.

The mistake in step 2 is to swap the secret instead of adding it: for a few minutes, deliveries signed with the old secret (already in flight, or retries of older failures) fail verification. They are retried and succeed later, so nothing is lost, but the integrator sees a burst of 401s in their logs and opens a ticket. The guide says "add, then remove" in bold.

## Staging

Staging subscriptions have their own secrets and their own egress addresses. An integrator who verifies staging deliveries with the production secret gets "invalid signature" on everything and, in three cases in 2026, concluded our staging was broken. The subscription screen shows the environment name next to the secret hash prefix since HF-3104 for this reason.

## What support may say and not say

May: the algorithm, the header format, the skew rule, the first 4 characters of the secret's hash (to confirm which subscription they are looking at), the exact bytes we sent for a delivery id. May not: the secret, ever, even the last characters, even to the person who created it; a lost secret is rotated. This is written on the support playbook and on the macro, and there has been no exception.
