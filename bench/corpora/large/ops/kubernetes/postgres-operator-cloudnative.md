# PostgreSQL under CloudNativePG (HF-1215)

Since November 2025, after the Longhorn findings in [[longhorn-storage-lessons]].

## Cluster definition (summary of `components/postgres/overlays/prod/cluster.yaml`)

- `instances: 2`, image `postgresql:16.6` with PostGIS 3.4 (the operator's PostGIS variant).

- Storage: `local-path` StorageClass, 3 TB volume per instance, on the NVMe of the database nodes. `nodeSelector` on `hf.example/pool: database`, toleration for `workload=database`. Anti-affinity `required` on hostname so the two instances never share a node.

- `postgresql.parameters`: `shared_buffers: 64GB`, `effective_cache_size: 180GB`, `work_mem: 32MB`, `maintenance_work_mem: 2GB`, `max_connections: 200`, `wal_compression: on`, `checkpoint_timeout: 15min`, `max_wal_size: 16GB`, `log_min_duration_statement: 500ms`, `track_io_timing: on`.

- `minSyncReplicas: 0`, `maxSyncReplicas: 0`: asynchronous replication. Synchronous would have doubled commit latency for the API and the replica lag is under 100 ms in normal operation, measured. We accept losing the last few transactions in the disaster case where the primary node dies and its NVMe with it.

- `primaryUpdateStrategy: unsupervised` for minor versions (the operator does the switchover and update), `primaryUpdateMethod: switchover`.

## Backups

- WAL archiving continuous to the object store, bucket `hf-pg-backups-prod`, compressed with `gzip`, `maxParallel: 4`.

- Base backup daily at 01:00 through the operator's `ScheduledBackup`, retention `30d`. A base backup takes 35 minutes for 1.2 TB.

- Point-in-time recovery tested monthly by restoring into a `Cluster` named `restore-test` on the staging overlay, to a timestamp from the previous day, then running `SELECT count(*) FROM loads` and comparing with the value recorded in the test log. Last test 2026-05-12, restore took 52 minutes, count matched. The nightly staging restore (see the platform environments note) uses the same mechanism.

## Access

- `rw` Service (`hf-postgres-rw`) points at the primary, `ro` at the replica. The API's PgBouncer targets `rw`. Reporting queries from the data platform target `ro`.

- Roles created by the operator's `managed.roles`: `api` (owner of the app schema), `api_migrations`, `reporting` (read-only), `exporter`. Passwords are generated by the operator into Secrets, and the application reads `DATABASE_URL` from an ExternalSecret that composes it, see [[secrets-external-secrets-vault]].

- `statement_timeout` is set per role (`ALTER ROLE api SET statement_timeout = '8s'`), not globally, so the migration role and reporting are not limited.

## Switchover and failover

- Planned switchover: `kubectl cnpg promote hf-postgres hf-postgres-2`. Measured at 30 s of write unavailability, the API's retry on connection errors covers it without user-visible errors. Used during node maintenance, see [[runbook-node-drain-replace]].

- Unplanned failover: the operator promotes the replica after the primary is unreachable for `failoverDelay: 0` plus the liveness probe timings, about 40 s in the one real case (a kernel panic on `hf-db-01` in January 2026). The API saw 45 s of connection errors, retried, nobody outside the team noticed.

## Monitoring

The operator exposes metrics scraped by the ops Prometheus: replication lag, WAL archive status, backup age. Alerts: `PostgresReplicationLagHigh` (> 30 s for 5 min, warn), `PostgresWalArchiveFailing` (page), `PostgresBackupTooOld` (> 36 h, page), `PostgresConnectionsNearMax` (> 180, warn). The application-side metrics (query latency, PgBouncer pools) are described in the observability project.

## What we would change

The 2-instance layout means a maintenance on one node leaves us with a single instance for its duration. A third instance on a general worker with Longhorn storage as a "warm" replica was discussed and rejected: it would be the slow storage we just left, and it would be promoted by the operator in a failover. We prefer the 15 minute exposure during maintenance.

## Minor version updates done so far, and what the switchover does to connections

| Date | From | To | Method | Write unavailability |
|---|---|---|---|---|
| 2025-12-02 | 16.4 | 16.5 | unsupervised rolling update, replica first | 28 s |
| 2026-02-17 | 16.5 | 16.6 | same | 31 s |
| 2026-05-19 | 16.6 | 16.6 (image rebuild for PostGIS 3.4.3) | same | 30 s |

The operator updates the replica first (pod restart with the new image, about 2 minutes to be back in streaming), then performs a switchover to it, then updates the former primary, which becomes the replica. Total 6 to 8 minutes, of which the application sees the 30 s of switchover.

What happens to connections during the switchover, since it took a while to understand and it matters for the API's retry logic:

1. The operator sends a `CHECKPOINT` then a fast shutdown to the primary. Every open connection gets `FATAL: terminating connection due to administrator command`. PgBouncer marks its server connections dead.

2. The replica is promoted. The `rw` Service's endpoint is updated by the operator (it watches the instance roles), which takes 2 to 5 s to propagate to the node's Cilium datapath.

3. PgBouncer, which connects to the `rw` Service name, opens new server connections on the next client request. Because the first attempts land during the propagation window, PgBouncer's `server_connect_timeout` (15 s) and `server_login_retry` (15 s) can add up to a 15 s stall on top. Setting `server_login_retry` to 2 s brought the observed unavailability from 45 s to 30 s.

4. On the API side, DBAL throws a `ConnectionLost` on the first query of a request that hits a dead pooled connection. The API's `RetryConnectionMiddleware` retries the whole request handler once after 500 ms for idempotent requests (GET, and POST with an `Idempotency-Key`), which covers the mobile mutation pushes. Non-idempotent requests without a key get a 503 with `Retry-After: 5`. During the May update, 41 requests got that 503 and the clients retried them all.

The `ro` Service points at whichever instance is the replica, so reporting queries in flight on the old replica are killed when it is promoted, and the data platform's loader retries its batch. It has never complained.

One thing the operator does not do: warm the new primary's cache. The first minute after a switchover shows p95 query latency at 3× the usual on the loads search, then back to normal. `pg_prewarm` on the search indexes at promotion is HF-INFRA-430, not started, because a minute of slower search three times a year is not worth a hook.
