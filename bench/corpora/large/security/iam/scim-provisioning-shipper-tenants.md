# SCIM provisioning for enterprise shippers (HF-2130)

Three large shippers asked, in the same quarter, for their IT to manage Halden Freight users from their own directory instead of having an admin invite people by hand. HF-2130 shipped a SCIM 2.0 server in March 2026. It is customer-facing, so it lives in the API project's routing but the security model is ours.

## Scope

Users and Groups, that is all. `GET/POST/PUT/PATCH/DELETE /scim/v2/Users`, same for `/Groups`, plus `/ServiceProviderConfig`, `/ResourceTypes`, `/Schemas`. No custom schema extensions: the two attributes we care about beyond the core schema (`organizationId`, role) are derived, not sent.

One SCIM connection per organization, enabled by support (`organization_features.scim_enabled`). The organization gets a dedicated bearer secret generated by `ScimSecretIssuer`, shown once, stored hashed the same way as API keys (see [[api-key-hashing-and-prefix]]), prefixed `hfs_` so scanners can tell them apart. Rotation is the same overlap mechanism as [[api-keys-lifecycle]].

## User lifecycle

- **Create**: `userName` must be an email in a domain the organization has verified (`organization_domains`, verified by DNS TXT). A user in an unverified domain is rejected with SCIM error 400 `invalidValue`. This is the rule that prevents a shipper from provisioning someone else's employees.

- **Update**: `active: false` sets `users.disabled_at` and revokes sessions (see [[session-revocation-on-role-change]]). It does not delete. `DELETE` also only disables, and returns 204. We never hard-delete through SCIM because the user may have created loads and invoices that must stay attributed. Real erasure goes through the compliance process.

- **Reactivate**: `active: true` clears `disabled_at`. Sessions are not restored.

Users created by SCIM have `users.managed_by = 'scim'`. The invite UI refuses to edit them and says why. Twelve tickets in the first month came from admins who did not understand why "edit" was greyed out, hence the explicit banner.

## Groups to roles

The customer's directory groups arrive as SCIM Groups. `scim_group_mappings (organization_id, external_group_id, role_id)` maps them to roles from [[roles-permissions-model]] (system or custom roles of that organization). A user in no mapped group gets `shipper_viewer`. A user in two mapped groups gets both roles, and permissions are the union.

The mapping is configured by the organization admin in `/settings/scim`, not by SCIM itself, because letting the directory define roles by name would have coupled our role codes to the customer's naming.

## Things that bit us

- One identity provider sends `PATCH` with `Operations[].path` like `members[value eq "..."]`. The filter grammar had to be implemented, at least the `eq` subset. Two days.

- Another sends `emails[].primary` as the string `"True"`. We coerce.

- Timeouts: the first full sync of a 1 900 user tenant arrived as 1 900 sequential `POST`s in 4 minutes and tripped the per-organization rate limit. SCIM traffic now has its own bucket (600 requests per minute per organization).

## Audit

Every SCIM change produces `member.invited`, `member.role_changed` or `member.removed` in the audit trail with `actor_type = 'apikey'` and the SCIM secret id as actor, plus `details.via = 'scim'`. See [[audit-trail-schema]].
