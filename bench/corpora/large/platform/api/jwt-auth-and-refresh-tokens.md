# Authentication: JWT access + opaque refresh

## Access token

- Signed ES256 with a key pair per environment. The private key is mounted from the `api-jwt-signing` secret (see the ops notes on external secrets), public key published at `GET /.well-known/jwks.json` with a `kid`. Key rotation: add the new key to the JWKS, switch signing, remove the old key 24 h later. Done twice so far, both without incident.

- Lifetime 15 minutes. Claims: `sub` (user uuid), `org` (carrier or shipper uuid), `role` (`driver`, `dispatcher`, `shipper_admin`, `carrier_admin`, `support`), `scope` (space-separated), `iat`, `exp`, `jti`.

- No revocation list for access tokens. 15 minutes is the blast radius when a user is disabled. Support was told this and accepted it.

- The web front stores it in memory only. The driver app stores it in the platform keychain (see the mobile note on offline login).

## Refresh token

- 32 random bytes, base64url, generated by `random_bytes()`. Stored as SHA-256 in `refresh_tokens (id, user_id, token_hash, family_id, issued_at, expires_at, revoked_at, replaced_by_id, device_label)`.

- Lifetime: 30 days for `driver` (the app must work for a driver who does not log in for weeks), 12 hours for `dispatcher` and admin roles, 7 days for `shipper_admin`.

- Rotation on every use: `POST /v2/auth/refresh` returns a new access token and a new refresh token, marks the old one `replaced_by_id`.

- Reuse detection: presenting a refresh token that already has `replaced_by_id` set revokes the whole `family_id`. That family is all tokens descending from one login. The user has to log in again, and `auth.refresh_reuse_detected` is logged with the `device_label`. We have seen 3 real cases, all from a driver app bug where two isolates refreshed in parallel (fixed in app 4.4.1 with a mutex around refresh).

## Login

`POST /v2/auth/login` with e-mail + password for web roles, `POST /v2/auth/driver-login` with phone number + 6-digit PIN for drivers. PIN hashing is argon2id with the Symfony `PasswordHasher` defaults. Rate limiting on login: 10 attempts per 15 minutes per identifier and per IP, via the `login` limiter in `config/packages/rate_limiter.yaml`, response 429 with the standard envelope.

## Service accounts

Carrier TMS integrations use `client_credentials`: `POST /v2/auth/token` with `client_id` and `client_secret`. Secrets are stored hashed, shown once at creation in the admin UI. The resulting access token has `role: integration` and a 1 hour lifetime, no refresh token.

## Why not sessions

The API is stateless behind 45 pods, and the driver app is offline for hours at a time. A server session would have to be replicated and would still not help the offline case.
